## 1. Core Data Structures

### MapBlock

A `MapBlock` is a 16×16×16 node cube. Important fields:

- `m_generation_stage` (`u8`) — current generation stage of this block (see `src/mapgen/mapgen_stage.h` for the `STAGE_*` constants). `STAGE_NONE` (0) = not yet generated; `STAGE_COMPLETE` (255) = all mapgen passes finished. The `isGenerated()` helper returns `true` when `m_generation_stage >= STAGE_COMPLETE`. Border blocks from overgeneration are left at `STAGE_NONE`.
- `m_lighting_complete` (`u16`) — bitmask indicating which of the 6 neighbor directions have been lit.
- `m_modified` (`ModifiedState`) — `MOD_STATE_CLEAN`, `MOD_STATE_WRITE_AT_UNLOAD`, or `MOD_STATE_WRITE_NEEDED`.
- A `ModReason` bitmask tracks *why* it was modified (e.g., `MOD_REASON_SET_GENERATED`, `MOD_REASON_VMANIP`, `MOD_REASON_SET_NODE`, …).

### EmergeManager

Lives on the main server thread and owns:

- `m_blocks_enqueued` — `map<v3s16, BlockEmergeData>`: all pending emerge requests, one entry per unique block position.
- `m_peer_queue_count` — per-peer block count for rate-limiting.
- `m_threads` — a vector of `EmergeThread*` (1–4 by default, capped due to lock contention; the exact count is `min(4, logical_cores - 2)`).
- `m_mapgens` — one `Mapgen*` per thread, so threads can generate truly in parallel without sharing noise state.

### BlockEmergeData

Stored in `m_blocks_enqueued`. Carries:

- `flags` — `BLOCK_EMERGE_ALLOW_GEN` (generation is allowed) and/or `BLOCK_EMERGE_FORCE_QUEUE` (bypass per-peer queue limits).
- A list of completion callbacks `(blockpos, EmergeAction, param)`.

### EmergeAction (result codes)

```cpp
EMERGE_CANCELLED    // Dropped from queue (queue full, shutdown, etc.)
EMERGE_ERRORED      // Generation failed
EMERGE_FROM_MEMORY  // Block was already loaded in RAM
EMERGE_FROM_DISK    // Block was loaded from the world database
EMERGE_GENERATED    // Block was freshly generated by mapgen
```

## 2. Overgeneration

### What it is

When mapgen generates a chunk, it does **not** generate just the 5×5×5-block chunk it was asked for. It generates a slightly larger area that extends **1 extra block in every direction**:

```cpp
// src/servermap.h
constexpr static v3s16 EMERGE_EXTRA_BORDER{1, 1, 1};

// Result:
full_bpmin = bpmin - EMERGE_EXTRA_BORDER;   // one block further in every axis
full_bpmax = bpmax + EMERGE_EXTRA_BORDER;
```

### Why it is needed

1. **Noise continuity** — 3D Perlin/simplex noise fields need a context window larger than the chunk so that interpolated values at chunk boundaries are continuous.
2. **Cave walls** — Cave generators look at neighbors to decide whether a node should be hollowed; without the border, caves would have seam artifacts at chunk boundaries.
3. **Lighting** — Sunlight propagation and torch light spreading both need to look one block outside the chunk to correctly compute light at the edge nodes.
4. **Decorations and ores** — Trees, plants, and ore veins can protrude slightly into adjacent blocks; the border gives them somewhere to land.

### Important nuance

The border blocks are generated (VoxelManipulator is written into them) but are **not** advanced beyond `STAGE_NONE` afterward. Only the central chunk's blocks get `setGenerated(true)` (i.e. `m_generation_stage = STAGE_COMPLETE`). This prevents the map from treating the border slices as authoritative and avoids double-generation problems if a neighbouring chunk is requested later.

## 4. The Lua Mapgen API

### Callback Registration

```lua
minetest.register_on_generated(function(minp, maxp, blockseed)
    -- Runs in EmergeThread context after makeChunk(), before finishBlockMake()
    local vm = minetest.get_mapgen_object("vmanip")
    -- Read/modify/write nodes via vm:get_node(pos) / vm:set_node(pos, node)
    -- vm:write_to_map(true) to flush changes back
end)
```

### VoxelManipulator Lua API

The `vm` object wraps `MMVManip` (the same scratch-buffer used internally):

```lua
vm:read_from_map(p1, p2)          -- Load additional area (outside chunk)
vm:write_to_map(update_liquids)   -- Flush back
vm:get_node(pos)                  -- {name, param1, param2}
vm:set_node(pos, node)
vm:get_node_at_index(idx)         -- Fast flat-array access
vm:calc_lighting(p1, p2)          -- Recalculate lighting after edits
vm:update_liquids()               -- Queue liquid transforms
```

### Access to Generation Context

```lua
minetest.get_mapgen_object("heightmap")  -- Flat array[mapgen_chunksize²]
minetest.get_mapgen_object("biomemap")   -- Flat array[mapgen_chunksize²]
minetest.get_mapgen_object("heatmap")    -- Climate heat
minetest.get_mapgen_object("humidmap")   -- Climate humidity
minetest.get_mapgen_object("gennotify")  -- {dungeons=[…], temples=[…], …}
```

### Registering Biomes / Ores / Decorations

These are registered once and executed inside `makeChunk()`:

```lua
minetest.register_biome({…})
minetest.register_ore({…})
minetest.register_decoration({…})
minetest.register_schematic({…})

-- Runtime placement helpers:
minetest.generate_ores(vm, p1, p2)
minetest.place_schematic_on_vmanip(vm, pos, schematic, rotation, …)
```

## 5. Block Status — The Full Picture

| Status / Flag | Where | Meaning |
|---|---|---|
| `m_generation_stage == STAGE_NONE` | `MapBlock` | Block exists in RAM but mapgen has not finalised it (e.g., border block, or loaded-but-ungenerated legacy chunk) |
| `m_generation_stage == STAGE_COMPLETE` | `MapBlock` | Mapgen ran over this block and it is the authoritative central-chunk result |
| `MOD_STATE_CLEAN` | `MapBlock::m_modified` | No changes since last save |
| `MOD_STATE_WRITE_AT_UNLOAD` | `MapBlock::m_modified` | Save when evicted from RAM |
| `MOD_STATE_WRITE_NEEDED` | `MapBlock::m_modified` | Save as soon as the map-save timer fires |
| `BLOCK_EMERGE_ALLOW_GEN` | `BlockEmergeData::flags` | OK to run full mapgen if block is not on disk |
| `BLOCK_EMERGE_FORCE_QUEUE` | `BlockEmergeData::flags` | Bypass per-peer queue limits |
| `EMERGE_FROM_MEMORY` | `EmergeAction` | Block was already loaded in RAM |
| `EMERGE_FROM_DISK` | `EmergeAction` | Loaded from world database |
| `EMERGE_GENERATED` | `EmergeAction` | Freshly generated this session |
| `EMERGE_CANCELLED` | `EmergeAction` | Request was dropped (queue full, shutdown) |
| `EMERGE_ERRORED` | `EmergeAction` | Something went wrong during generation |
| `m_lighting_complete` bitmask | `MapBlock` | 6 bits, one per face-direction, indicating whether light has been propagated from that side |

## 6. How the Client Requests Blocks (and the Server Sends Them)

### There Is No Explicit "Request" Packet

Clients do **not** send "please send me block X" messages. Instead:

1. **Client sends `TOSERVER_PLAYERPOS`** every frame. Embedded in this packet is `wanted_range` — the player's configured viewing distance in map blocks.
2. **Server iterates** over all connected clients each tick (`~0.05 s`) and calls `RemoteClient::GetNextBlocks()` to decide which blocks each client should receive next.

### `RemoteClient::GetNextBlocks()` — the Priority Algorithm

Located in `src/server/clientiface.cpp`. Runs on the **server main thread**.

```
1. If m_blocks_sending.size() >= m_max_simul_sends → return (queue full)

2. Get player position (from PlayerSAO)
   Predict future position:
     playerpos_predicted = playerpos + normalize(velocity) * MAP_BLOCKSIZE

3. Get camera position + direction + FOV

4. wanted_range = player's requested range (clamped to max_block_send_distance)

5. Expand outward from d = m_nearest_unsent_d (resume point from last call):
   for d = m_nearest_unsent_d .. wanted_range:
     for each block_pos on the shell at distance d (cube surface):
       a. Skip if already in m_blocks_sent or m_blocks_sending
       b. isBlockInSight(block_pos, camera_pos, camera_dir, fov)?
          → frustum culling with an extra 10 % angular margin
       c. Server-side occlusion culling (isBlockOccluded)?
          → uses m_blocks_occ cache to avoid re-testing recently culled blocks
       d. Compute priority = distance + camera_alignment_bonus
       e. Append PrioritySortedBlockTransfer{priority, pos, peer_id}

     if shell was full (many blocks) → stop to limit per-call CPU cost
     else → continue to next shell

6. Update m_nearest_unsent_d (for next call to resume here)
```

**Key parameters:**

| Setting | Default | Effect |
|---|---|---|
| `max_block_send_distance` | 12 blocks | Absolute max distance to send blocks |
| `block_send_optimize_distance` | 4 blocks | Skip air-only blocks beyond this |
| `block_cull_optimize_distance` | 3 blocks | Aggressive occlusion culling beyond this |
| `max_block_generate_distance` | 6 blocks | Trigger mapgen up to this distance |
| `max_simultaneous_block_sends_per_client` | 25 | Per-client in-flight cap |

### `Server::SendBlocks()` — Global Dispatch

```
Each tick (~0.05 s):
1. Collect priority-sorted blocks from every client into one big queue
2. std::sort the queue (lowest priority number = highest priority)
3. Global cap: max_blocks_to_send = (players + max_users) * per_client / 4 + 1
4. For each entry in queue (until cap):
   a. MapBlock *block = map.getBlockNoCreateNoEx(pos) → skip if nil
   b. If block not yet generated → enqueueBlockEmerge(pos, allow_gen=true)
      → skip for this tick, come back next time
   c. Serialize block (cached if multiple clients need the same block)
   d. Send TOCLIENT_BLOCKDATA packet
   e. client->SentBlock(pos) → pos enters m_blocks_sending
```

### Block-State Bookkeeping in `RemoteClient`

| Field | Meaning |
|---|---|
| `m_blocks_sent` | Blocks the client has fully received and ACKed; won't be re-sent unless `SetBlockNotSent()` is called |
| `m_blocks_sending` | Blocks "in flight" (sent, awaiting `TOSERVER_GOTBLOCKS` ACK) |
| `m_blocks_occ` | Occlusion-culled block cache (reset when player moves or distance changes) |
| `m_nearest_unsent_d` | Shell-distance resume pointer |

**State transitions:**

```
                  SentBlock(pos)
not known ──────────────────────→ m_blocks_sending
               GotBlock(pos)
m_blocks_sending ───────────────→ m_blocks_sent
               SetBlockNotSent(pos)
m_blocks_sending / m_blocks_sent → not known
  (block was modified, player moved far, etc.)
```

`SetBlockNotSent()` is called whenever a block is modified (via `MapEditEvent` dispatch) or when the player moves far enough to trigger a full rescan.

### Network Packet Reference

| Packet | Direction | Payload |
|---|---|---|
| `TOCLIENT_BLOCKDATA` | Server → Client | `v3s16` position + serialised `MapBlock` data |
| `TOSERVER_GOTBLOCKS` | Client → Server | `u8` count + `v3s16[]` positions (ACK) |
| `TOSERVER_DELETEDBLOCKS` | Client → Server | `u8` count + `v3s16[]` positions (removed by client) |
| `TOSERVER_PLAYERPOS` | Client → Server | position, pitch, yaw, FOV, **`wanted_range`** |

## 7. Complete End-to-End Flow: "Block Appears on Screen"

```
T0  Player moves / logs in
     └─ Server: GetNextBlocks() → block X not in m_blocks_sent

T1  Block X not in RAM
     └─ emerge->enqueueBlockEmerge(peer_id, X, allow_gen=true)

T2  EmergeThread picks up request
     └─ Not on disk → EMERGE_GENERATED path
     └─ initBlockMake(): create MapBlocks + MMVManip
     └─ makeChunk(): terrain, caves, ores, decorations
     └─ Lua on_generated(): mods modify vmanip
     └─ finishBlockMake(): blit, lighting, setGenerated(true) [m_generation_stage = STAGE_COMPLETE]
     └─ runCompletionCallbacks() → dispatchEvent to server

T3  Server main thread dispatches MapEditEvent
     └─ SetBlockNotSent(X) for all relevant clients
     └─ Block X now eligible to be sent

T4  Next Server::SendBlocks() tick (~0.05 s)
     └─ GetNextBlocks() returns X in priority queue
     └─ block->serialize() (zlib or zstd compressed node data)
     └─ Send TOCLIENT_BLOCKDATA packet
     └─ client->SentBlock(X) → X enters m_blocks_sending

T5  Client receives TOCLIENT_BLOCKDATA
     └─ handleCommand_BlockData(): deserialise into MapBlock
     └─ addUpdateMeshTaskWithEdge(X, ack_to_server=true)

T6  Client mesh thread picks up task
     └─ MapBlockMesh::MapBlockMesh():
          – face visibility culling per node
          – per-vertex light (smooth lighting, day + night banks)
          – transparent-face BSP tree for depth sorting
          – bake into Irrlicht IMesh
     └─ mesh assigned to block

T7  Client main loop sees completed mesh
     └─ sendGotBlocks({X}) → TOSERVER_GOTBLOCKS

T8  Server receives TOSERVER_GOTBLOCKS
     └─ client->GotBlock(X): m_blocks_sending → m_blocks_sent
     └─ Block X will NOT be re-sent unless it is modified

T9  Next render frame
     └─ Block X's mesh is drawn (frustum + distance culled)
     └─ Transparent faces sorted via BSP traversal from camera
```

## 8. Lighting in Mapgen

Lighting is calculated in two passes inside `finishBlockMake()`, operating over the **overgenerated** area (so border edges are correctly lit):

1. **`propagateSunlight(full_bpmin, full_bpmax)`** — traces rays downward from the top of the area, marking nodes with `LIGHT_SUN` until an opaque node is hit.
2. **`spreadLight(full_bpmin, full_bpmax)`** — BFS flood-fill from every light-emitting node (sun entry points + torch-like nodes). Each step decrements light by 1/15. Stops at opaque nodes.

### Two Independent Light Banks

| Bank | Storage | Meaning |
|---|---|---|
| Day (`param1 >> 4`) | Upper nibble | Sunlight; changes with the day/night cycle |
| Night (`param1 & 0xF`) | Lower nibble | Artificial light (torches, etc.); constant |

The client combines both banks at render time based on the current time-of-day, enabling smooth day/night transitions without re-sending any block data.

### Why Overgeneration Is Required for Lighting

```cpp
void Mapgen::calcLighting(v3s16 nmin, v3s16 nmax,            // actual chunk
                          v3s16 full_nmin, v3s16 full_nmax)  // + border
{
    // Sunlight arrives from neighbours; without the border,
    // edge nodes would be incorrectly dark.
    propagateSunlight(full_nmin, full_nmax);
    spreadLight(full_nmin, full_nmax);
}
```

### Client-Side Smooth Lighting

Each vertex in a `MapBlockMesh` stores the average light level of the surrounding corner nodes, converting the 0–15 integer value to an RGB colour. This produces smooth gradients across faces without any extra node data.

Transparent blocks (glass, water) require correct depth ordering. `MapBlockMesh` builds a **BSP tree** from all transparent triangles at construction time; at render time the tree is traversed from the current camera position to emit triangles in far-to-near order, ensuring correct alpha blending.

## 9. Summary of Design Principles

1. **Pull-based from the server side** — the server decides what the client sees; there is no per-block request packet from the client.
2. **Nearest-first with camera awareness** — blocks directly ahead of the player (and closest) are prioritised, with frustum and occlusion culling saving significant bandwidth and CPU.
3. **Overgeneration solves boundary problems** — 1-block borders ensure correct noise, cave, lighting, and decoration behaviour at chunk edges, without ever marking those border blocks as "truly generated".
4. **Asynchronous generation pipeline** — mapgen runs in EmergeThread(s), completely independent of the server tick; blocks arrive in the send queue when they are ready.
5. **Persistent sent-set** — `m_blocks_sent` prevents re-sending unchanged blocks; `SetBlockNotSent()` surgically invalidates only what changed.
6. **Thread-safe Lua** — each EmergeThread carries its own `EmergeScripting` instance so `register_on_generated` callbacks run safely in parallel with one another and with the server thread.
